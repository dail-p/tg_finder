# RESEARCH-glm-5.2 — Умный поиск по Telegram-каналам

> Документ: архитектурный разбор + план работ для субагентов.
> Модель-автор: z-ai/glm-5.2
> Статус проекта: пустой (greenfield).

---

## 1. Постановка задачи

Бот-помощник, который отвечает на вопросы пользователя по содержимому заранее заданного набора Telegram-каналов.

**Ключевые сценарии:**
1. **Ответ по тематике канала.** Пользователь спрашивает «как сварить солянку?» — информация разбросана по разным постам кулинарного канала. Бот синтезирует связный ответ со ссылками на исходные посты.
2. **Пачки каналов.** Пользователь группирует каналы в «пачку» (например, все новостные) и ищет ответ сразу по всей пачке.
3. **Честное «не знаю».** Если в выбранном канале/пачке релевантной информации нет — бот прямо об этом сообщает, ничего не выдумывая.
4. **Ответ, а не дамп постов.** Возвращать конкретный ответ на вопрос + ссылки-источники, а не копии постов as-is.

Суть — **умный RAG-поиск по ограниченному списку каналов**.

## 2. Разбор архитектур

### Архитектура A — Чистый RAG с периодической синхронизацией
- Воркер по расписанию тянет историю постов из каналов (через userbot/MTProto).
- Каждый пост дробится на чанки, эмбеддится, кладётся в векторную БД.
- На запрос: эмбеддинг запроса → top-k чанков → LLM генерирует ответ с цитатами.

**Плюсы:** стандартная, понятная схема; хорошо склеивает инфу из разных постов.
**Минусы:** данные устаревают между синхронизациями; лишняя нагрузка при ре-индексации; нельзя гарантировать свежесть.

### Архитектура B — Событийная (индексация при постинге)
- Userbot слушает новые сообщения в каналах в реальном времени (event NewMessage).
- Новый пост сразу чанкуется и индексируется.
- Поиск — тот же RAG, но всегда по свежим данным.

**Плюсы:** мгновенная свежесть; нет полной ре-индексации; меньше лишней нагрузки.
**Минусы:** пропуски при простое/рестарте; нужна начальная бэкфилл-выгрузка истории; сложнее обрабатывать редактирования/удаления постов.

### Архитектура C — Гибридная (рекомендуемая)
- **B + A:** событийная индексация в реальном времени **плюс** периодическая сверка (reconciliation) для подстраховки и бэкфилла пропущенного.
- **Гибридный поиск:** семантический (векторы) + лексический (BM25/FTS) с reciprocal rank fusion.
- Эвристики + LLM-судья для детекции «нет информации».

**Плюсы:** свежесть + надёжность; лучшее качество поиска (слова + смысл); устойчивость к пропускам.
**Минусы:** самая сложная в реализации; больше компонентов.

### Архитектура D — Агентная (LLM с инструментом поиска)
- LLM-агент сам формулирует поисковые запросы, реформулирует, делает несколько итераций, решает когда «достаточно».
- Под капотом — тот же ретривер.

**Плюсы:** лучшее качество на сложных/многошаговых вопросах.
**Минусы:** дороже (несколько LLM-вызовов); выше латентность; сложнее дебаг.

### Архитектура E — Только полнотекстовый поиск (без эмбеддингов)
- BM25/FTS по постам, выдача ранжированных сниппетов, лёгкая LLM-суммаризация.

**Плюсы:** максимально просто; дёшево; точное совпадение слов.
**Минусы:** плохо понимает синонимы/перефразирования (солянка = густой суп); слабее склеивает разбросанную инфу.

## 3. Рекомендуемая архитектура: гибрид C

**Почему:** требования (свежесть при постинге + честное «не знаю» + склейка постов + пачки) лучше всего покрываются сочетанием событийной индексации, гибридного поиска и LLM-генерации с проверкой релевантности. Агентный слой (D) можно добавить позже как улучшение для сложных кейсов.

**Принципиальная схема:**

```
┌─────────────── Telegram ───────────────┐
│  Каналы (источники)                     │
└───┬───────────────────────────▲─────────┘
    │ история (бэкфилл)         │ новые посты (events)
    ▼                           │
┌─────────────────────────────────────────┐
│ Ingestion (Telethon userbot)            │
│  - subscribe / listen NewMessage        │
│  - periodic reconciliation              │
│  - нормализация, дедуп, media-извлечение│
└───────────────┬─────────────────────────┘
                ▼
┌─────────────────────────────────────────┐
│ Indexing pipeline                       │
│  - chunking (по постам/абзацам)         │
│  - embeddings (мультлингв. модель)      │
│  - pgvector + tsvector (FTS)            │
└───────────────┬─────────────────────────┘
                ▼
┌──────────────── PostgreSQL (pgvector) ──┐
│ posts, chunks, channels, packs, users   │
│ vector index + FTS index                │
└───────────────┬─────────────────────────┘
                ▼
┌─────────────────────────────────────────┐
│ Retrieval (hybrid)                      │
│  vector top-k ⊕ BM25 top-k → RRF fusion │
│  фильтр по channel/pack                 │
│  порог релевантности                    │
└───────────────┬─────────────────────────┘
                ▼
┌─────────────────────────────────────────┐
│ Generation (LLM)                        │
│  контекст из чанков → ответ + цитаты    │
│  LLM-судья: «хватает ли инфы?»          │
│  если нет → «не найдено»                │
└───────────────┬─────────────────────────┘
                ▼
┌─────────────────────────────────────────┐
│ Bot (aiogram)                           │
│  команды, выбор пачки/канала, диалог    │
└─────────────────────────────────────────┘
```

**Цитирование источников.** У каждого поста есть ссылка вида `https://t.me/<channel>/<message_id>` (для публичных) или `tg://privatepost?channel=...&post=...` (для приватных). Чанк хранит ссылку-источник → ответ содержит `[1]`, `[2]` со ссылками.

## 4. Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Язык | Python 3.11+ | экосистема TG + ML |
| Userbot (чтение каналов) | **Telethon** (MTProto) | чтение постов каналов, подписка на события, работа от имени юзера |
| Bot API (диалог с юзером) | **aiogram 3** | асинхронный, зрелый, команды/кнопки/FSM |
| БД | **PostgreSQL 16 + pgvector** | один компонент: метаданные + векторы + FTS (tsvector). Меньше инфры. |
| FTS | Postgres `tsvector` + GIN (русская конфигурация) | лексический поиск без доп. сервисов |
| Эмбеддинги | `intfloat/multilingual-e5-large` (self-host) или OpenAI `text-embedding-3-large` | мультилингв, хорошо на русском |
| LLM (генерация/судья) | GPT-4o-mini / Claude / open-модели через шлюз | баланс цена/качество; судья — дешевле |
| Очередь/задачи | APScheduler (in-process) или Celery+Redis при росте | reconciliation, ретраи |
| Контейнеризация | Docker + docker-compose | локальный запуск + прод |
| Миграции | Alembic | версионирование схемы |
| Тесты | pytest, pytest-asyncio | |

> Альтернатива векторной БД: Qdrant/Milvus при масштабе. На старте pgvector достаточно и упрощает стек.

## 5. Модель данных (схема БД)

```
users(id tg_id, username, created_at)

channels(id, tg_channel_id, username, title, access_hash, is_public,
         last_synced_msg_id, last_synced_at, added_by_user_id, created_at)

packs(id, owner_user_id, name, description, created_at)
pack_channels(pack_id, channel_id)   -- m2m

posts(id, channel_id, tg_message_id, date, text, raw_json, media_meta,
      link, edited_at, deleted bool,
      UNIQUE(channel_id, tg_message_id))

chunks(id, post_id, ordinal, text, embedding vector(N), fts tsvector,
       channel_id, pack_ids[])   -- pack_ids денормализован для быстрого фильтра
       -- индексы: HNSW на embedding; GIN на fts; btree на channel_id

search_logs(id, user_id, query, selected_scope_type, selected_scope_id,
            retrieved_count, answered_bool, created_at)  -- аналитика/дообучение
```

**Индексы:**
- `chunks.embedding` — HNSW (pgvector).
- `chunks.fts` — GIN.
- `chunks.channel_id`, `chunks.pack_ids` — для фильтрации скоупа.

**Скоуп поиска** — канал ИЛИ пачка. При поиске по пачке фильтруем `channel_id IN (каналы пачки)` (или по `pack_ids`).

## 6. Потоки данных

### 6.1 Ingestion (событийный + reconciliation)
1. При добавлении канала: бэкфилл истории (с пагинацией, с rate-limit), индексация.
2. Telethon `events.NewMessage` по всем подписанным каналам → индексация нового поста сразу.
3. Раз в N (например, час) — reconciliation: сверка `last_synced_msg_id`, добор пропущенного, пометка удалённых/изменённых.
4. При редактировании поста — переиндексация чанков этого поста.

### 6.2 Query (поиск ответа)
1. Юзер выбирает скоуп (канал или пачку) + вводит вопрос.
2. Генерация эмбеддинга вопроса.
3. Гибридный поиск: vector top-k **и** FTS top-k по скоупу → RRF-слияние.
4. Порог релевантности: если max score < threshold → кандидатов нет → сразу «не найдено».
5. LLM-генерация: промпт с контекстом (чанки + ссылки) → ответ + цитаты.
6. LLM-судья (или inline-инструкция): если в контексте нет нужного — вернуть «информации нет».
7. Лог в `search_logs`.

### 6.3 Управление пачками
- `/pack create <name>` — создать пачку.
- `/pack add <pack> <channel>` — добавить канал в пачку (с автоматическим бэкфиллом).
- `/pack list`, `/pack remove`, `/pack search <pack> <вопрос>`.
- FSM aiogram для пошагового диалога.

## 7. Детекция «нет информации» (требование 3)

Многоуровневая защита от галлюцинаций:
1. **Порог ретривера:** top-score ниже阈值 → «не найдено» без вызова LLM.
2. **LLM-судья:** отдельный дешёвый промпт «есть ли в контексте ответ на вопрос? да/нет». Если «нет» — отвечаем «информации по запросу нет».
3. **Запрет фантазий:** в системный промпт генератора жёстко: «отвечай только на основе контекста; если данных недостаточно — скажи что информации нет; обязательно цитируй источники».
4. Цитаты обязательны: ответ без валидных ссылок считается невалидным.

## 8. План работ для субагентов

Каждая задача самодостаточна (вход/выход/acceptance), чтобы субагент мог взять её в работу. Порядок ≠ строго обязательный, но сверху вниз минимизирует блокировки.

### Задача S1 — Скелет проекта и tooling
**Вход:** пустой репозиторий.
**Выход:** Python-проект (pyproject/uv), структура каталогов `app/{bot,ingest,indexing,retrieval,generation,db,config}`, ruff + mypy, pre-commit, `.env.example`, `docker-compose.yml` (postgres+pgvector), `Makefile`, `AGENTS.md` с командами lint/typecheck/test.
**Acceptance:** `make lint && make typecheck && make test` проходят; compose поднимает БД с расширением pgvector.

### Задача S2 — Конфиг и секреты
**Вход:** S1.
**Выход:** pydantic-settings (`Settings`): `TG_API_ID/HASH`, `TG_BOT_TOKEN`, `TG_SESSION_STRING`, `DATABASE_URL`, `EMBEDDING_*`, `LLM_*`, параметры sync-интервалов/порогов. Загрузка из `.env`.
**Acceptance:** приложение стартует и читает конфиг; валидация обязательных полей.

### Задача S3 — Схема БД и миграции (Alembic)
**Вход:** раздел 5 документа.
**Выход:** модели SQLAlchemy 2 + Alembic-миграции: `users, channels, packs, pack_channels, posts, chunks` (с `vector`, `tsvector`), индексы HNSW/GIN, `CREATE EXTENSION vector`.
**Acceptance:** `alembic upgrade head` разворачивает схему; тесты CRUD на каждую таблицу зелёные.

### Задача S4 — Userbot ingestion (Telethon)
**Вход:** S2, S3.
**Выход:** модуль `app/ingest`:
- подключение по `session_string`;
- `backfill_channel(channel)` с пагинацией и rate-limit;
- подписка `events.NewMessage` по всем каналам из БД;
- обработка edit/delete;
- запись в `posts` (дедуп по `channel_id+tg_message_id`), обновление `last_synced_msg_id`.
**Acceptance:** на тестовом канале бэкфилл заполняет `posts`; новый пост появляется в БД ≤ 5с; edit переиндексирует.

### Задача S5 — Индексация (chunking + embeddings + FTS)
**Вход:** S3, S4.
**Выход:** модуль `app/indexing`:
- chunking (пост → 1+ чанков по абзацам, ~512 токенов, overlap);
- генерация эмбеддингов (провайдер-абстракция: local e5 или OpenAI);
- запись `chunks.embedding` + заполнение `chunks.fts` (`to_tsvector('russian', text)`);
- `pack_ids` пересчитывается при изменении состава пачек.
**Acceptance:** для тестовых постов есть чанки с вектором и fts; изменение пачки обновляет `pack_ids`.

### Задача S6 — Управление каналами и пачками (сервис + API бота)
**Вход:** S3.
**Выход:** сервисный слой `app/packs`:
- `add_channel`, `remove_channel`, `list_channels`;
- `create_pack`, `add_channel_to_pack`, `remove_channel_from_pack`, `list_packs`, `list_pack_channels`;
- триггер бэкфилла при добавлении канала.
**Acceptance:** юнит-тесты покрывают все операции; m2m консистентен.

### Задача S7 — Гибридный retrieval
**Вход:** S5.
**Выход:** модуль `app/retrieval`:
- `search(query_text, scope_type, scope_id, top_k)`:
  - эмбеддинг запроса → pgvector top-k (косинус);
  - FTS top-k (ts_rank_cd);
  - RRF-слияние;
  - фильтр по скоупу (channel / pack);
  - возврат чанков со ссылками и скорами;
- порог релевантности (`Settings.relevance_threshold`).
**Acceptance:** на тестовом корпусе релевантные чанки ранжируются выше; поиск по пачке фильтрует правильно; при отсутствии — пустой список.

### Задача S8 — Генерация ответа + судья «нет информации»
**Вход:** S7.
**Выход:** модуль `app/generation`:
- провайдер-абстракция LLM;
- промпт-шаблон: контекст (чанки + ссылки) + вопрос → ответ с цитатами `[1]`/`[2]`;
- жёсткая инструкция «только из контекста, иначе — нет информации»;
- LLM-судья (или inline-флаг) для подтверждения наличия ответа;
- форматирование ссылок (`https://t.me/...` / `tg://privatepost`).
**Acceptance:** на релевантном запросе — связный ответ с рабочими ссылками; на нерелевантном — «информации по запросу нет»; нет выдуманных фактов.

### Задача S9 — Bot-интерфейс (aiogram)
**Вход:** S6, S7, S8.
**Выход:** модуль `app/bot`:
- команды: `/start`, `/channel add/list`, `/pack create/list/add/remove/search`, `/ask <scope> <question>`;
- FSM для пошагового создания пачки и выбора скоупа;
- inline-кнопки выбора канала/пачки перед вопросом;
- длинные ответы с разбивкой; обработка ожидания (typing);
- запись в `search_logs`.
**Acceptance:** e2e-сценарий в тестовом канале: добавить канал → создать пачку → задать вопрос → получить ответ со ссылкой; задать нерелевантный вопрос → получить «не найдено».

### Задача S10 — Reconciliation scheduler
**Вход:** S4, S5.
**Выход:** APScheduler-задачи:
- периодический reconciliation (добор пропущенных сообщений, пометка удалённых);
- ретраи с экспоненциальной задержкой;
- метрики/логирование ошибок.
**Acceptance:** при пропуске событий (имитация простоя) последующий reconciliation добирает посты.

### Задача S11 — Тесты (unit + integration)
**Вход:** все.
**Выход:** pytest-наборы:
- фикстуры: тестовая БД (testcontainers или docker-compose), мок Telethon, мок LLM/embeddings;
- unit: chunking, RRF, промпты, сервисы пачек;
- integration: ingestion→indexing→retrieval→generation e2e на эталонном корпусе постов.
**Acceptance:** покрытие ключевых потоков; CI-зелёные.

### Задача S12 — Деплой и эксплуатация
**Вход:** все.
**Выход:** `Dockerfile` (multi-stage), `docker-compose.yml` (bot, ingest, scheduler, postgres+pgvector), healthchecks, volume для сессии Telethon, инструкция в `AGENTS.md`/`README`.
**Acceptance:** `docker compose up` поднимает всю систему; healthcheck бот-эндпоинта ок.

## 10. Риски и открытые вопросы

1. **Доступ к каналам.** Бот не может читать произвольные каналы — нужен userbot (Telethon) от аккаунта, подписанного на каналы. Решение: session-string юзера. Для приватных каналов — аккаунт должен быть участником.
2. **Rate limits / FloodWait.** Бэкфилл больших каналов упирается в лимиты MTProto. Решение: пагинация с backoff, постепенный бэкфилл, кэш `access_hash`.
3. **Свежесть vs пропуски.** При рестарте ingest-воркера события пропускаются. Решение: reconciliation по `last_synced_msg_id` (требование S10).
4. **Качество «нет информации».** Один порог может ошибаться. Решение: двухуровневая проверка (порог + LLM-судья, раздел 7).
5. **Эмбеддинги: цена vs self-host.** Self-host e5 дешевле, но нужен GPU/CPU-инференс. На старте — OpenAI API, позже self-host.
6. **Масштаб.** pgvector до ~млн векторов работает; дальше — Qdrant/Milvus. Архитектура изолирует retrieval-провайдер, миграция локальна.
7. **Редактирования/удаления постов.** Нужно корректно обновлять/помечать чанки, чтобы ссылки не вели в никуда. Решение: обработка edit/delete в S4 + перевычисление чанков поста.
8. **Приватные посты — формат ссылок.** Использовать `tg://privatepost?channel=...&post=...` для приватных, `https://t.me/...` для публичных.
9. **Язык.** Основной язык — русский: `tsvector` с конфигурацией `russian`, мультилингв-эмбеддинги, промпты на русском.
10. **Лицензии/ToS Telegram.** Использование userbot-сессии на пользовательском аккаунте — на свой риск; для прод-режима желательна отдельная «сервисная» учётная запись.
