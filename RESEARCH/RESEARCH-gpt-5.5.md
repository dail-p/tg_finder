# План работ: Telegram-бот умного поиска по каналам

## Цель продукта

Нужно разработать Telegram-бота, который отвечает на вопросы пользователя по ограниченному набору Telegram-каналов или по заранее созданным пачкам каналов.

Ключевая идея: это не глобальный поиск по Telegram, а управляемый умный поиск по подключенным источникам. Бот должен находить разрозненную информацию в постах, синтезировать конкретный ответ и давать ссылки на исходные сообщения.

## Функциональные требования

1. Бот отвечает на вопросы по тематике выбранного канала или пачки каналов.
2. Пользователь может создавать пачки каналов, например `Новости`, `Кулинария`, `Крипта`, и искать внутри выбранной пачки.
3. Если информации в подключенных каналах нет, бот должен прямо сказать, что ответа в доступных источниках не найдено.
4. Бот не должен возвращать посты как есть. Он должен формировать конкретный ответ на вопрос и прикладывать ссылки на источники.
5. Все существенные утверждения в ответе должны быть подкреплены найденными источниками.
6. Для приватных каналов и корпоративных пачек должны учитываться права доступа.

## Базовые пользовательские сценарии

### Сценарий 1. Вопрос по одному каналу

Пользователь выбирает канал про готовку и спрашивает: `Как сварить суп солянку?`

Бот ищет по постам этого канала, находит несколько сообщений с ингредиентами, этапами приготовления и советами, затем возвращает краткий рецепт со ссылками на посты.

### Сценарий 2. Вопрос по пачке каналов

Пользователь создает пачку `Новостные каналы`, добавляет туда несколько источников и спрашивает: `Что писали про запуск проекта X на этой неделе?`

Бот ищет по всем каналам пачки, группирует найденные факты и возвращает ответ с датами и ссылками.

### Сценарий 3. Нет информации

Пользователь спрашивает о теме, которой нет в проиндексированных постах.

Бот отвечает: `В подключенных каналах я не нашел подтвержденной информации по этому вопросу`, а не выдумывает ответ.

### Сценарий 4. Уточнение области поиска

Пользователь спрашивает слишком широко. Бот предлагает уточнить канал, пачку, дату или ключевые слова.

## Рассмотренные архитектуры

### Вариант 1. MVP RAG

Схема:

```text
Telegram channels
  -> ingestion
  -> raw posts storage
  -> cleaning/chunking
  -> embeddings
  -> vector search
  -> LLM answer with sources
  -> Telegram bot response
```

Плюсы:

- Быстрее всего реализовать первую версию.
- Не требует обучения собственной модели.
- Хорошо подходит для вопросов по смыслу.
- Можно сразу возвращать ссылки на источники.

Минусы:

- Чистый vector search может плохо искать точные имена, даты, тикеры и цитаты.
- Качество сильно зависит от чанкинга и embedding-модели.
- Нужны жесткие guardrails, чтобы LLM не додумывала факты.

Вывод: лучший стартовый вариант для MVP.

### Вариант 2. Гибридный RAG: BM25 + vector search + reranker

Схема:

```text
User query
  -> lexical search BM25 / full-text search
  -> semantic vector search
  -> merge by RRF or weighted score
  -> reranking
  -> answer generation with citations
```

Плюсы:

- Лучше работает с точными совпадениями.
- Лучше подходит для Telegram-контента, где много коротких постов, имен, дат, ссылок и хэштегов.
- Уменьшает риск пропуска релевантного поста.
- Reranker повышает точность перед генерацией ответа.

Минусы:

- Сложнее инфраструктура.
- Нужно настраивать веса, top-K и пороги релевантности.
- Reranking добавляет задержку и стоимость.

Вывод: рекомендуется как целевая архитектура после базового MVP.

### Вариант 3. Event-driven автообновление базы

Схема:

```text
New Telegram post
  -> listener
  -> queue
  -> processing worker
  -> upsert raw post
  -> re-chunk
  -> re-embed
  -> update search indexes
```

Плюсы:

- Новые посты быстро попадают в поиск.
- Сбор данных отделен от индексации.
- Ошибки можно ретраить через очередь.
- Удобно масштабировать обработчики.

Минусы:

- Нужны очередь, статусы обработки, retry и мониторинг.
- Нужно учитывать rate limits Telegram.
- Нужно обрабатывать редактирование и удаление постов.

Вывод: нужен после MVP, если важна свежесть данных.

### Вариант 4. Agentic retrieval

LLM управляет поиском: переформулирует вопрос, разбивает его на подзапросы, выполняет несколько retrieval-проходов, фильтрует по датам/каналам и собирает ответ.

Плюсы:

- Лучше для сложных аналитических вопросов.
- Может искать итеративно, если первый поиск слабый.
- Подходит для сравнений между каналами.

Минусы:

- Дороже и медленнее.
- Сложнее контролировать качество.
- Нужны лимиты шагов и трассировка действий агента.

Вывод: не для MVP. Добавлять позже для сложных исследовательских запросов.

### Вариант 5. Knowledge Graph

Из постов извлекаются сущности: люди, компании, проекты, даты, события, темы. Затем строятся связи между сущностями и постами.

Плюсы:

- Полезно для аналитики, мониторинга трендов и связей.
- Улучшает фильтры и объяснимость.

Минусы:

- Сильно повышает сложность.
- Нужны нормализация сущностей и отдельная модель данных.
- Для простого поиска по каналам избыточно.

Вывод: поздний этап, если продукт развивается в аналитическую систему.

### Вариант 6. Fine-tuning

Fine-tuning не должен быть способом хранения знаний из каналов. Новые посты появляются постоянно, поэтому знания должны храниться в индексе, а не в весах модели.

Где fine-tuning может быть полезен позже:

- классификация intent;
- выбор стратегии поиска;
- reranking;
- извлечение сущностей;
- стиль ответа;
- определение, когда нужно отказаться от ответа.

Вывод: не нужен на старте. Рассматривать после накопления логов, оценок качества и размеченных примеров.

## Рекомендуемая целевая архитектура

```text
Telegram Bot API / MTProto
        |
        v
Ingestion service
        |
        v
Raw posts storage: PostgreSQL
        |
        v
Processing pipeline
cleaning, normalization, chunking, metadata extraction
        |
        v
Indexes
PostgreSQL FTS / OpenSearch + pgvector / Qdrant
        |
        v
Hybrid retrieval
BM25 + vector search + RRF
        |
        v
Reranker
        |
        v
RAG answer generator
        |
        v
Telegram bot UI
```

Рекомендуемый путь разработки:

1. MVP RAG по ограниченному набору каналов.
2. Гибридный поиск BM25 + vector.
3. Reranking и улучшенный no-answer режим.
4. Автообновление индекса при новых постах.
5. ACL для приватных пачек и источников.
6. Agentic retrieval для сложных вопросов.
7. Knowledge Graph и fine-tuning только при доказанной необходимости.

## Telegram-специфика

### Bot API

Bot API хорошо подходит для:

- пользовательского интерфейса бота;
- команд, кнопок и диалогов;
- ответов пользователям;
- получения новых постов из каналов, где бот добавлен администратором;
- получения `channel_post` и `edited_channel_post` после подключения бота.

Ограничения Bot API:

- нет полноценного метода чтения истории канала;
- нельзя прочитать произвольный публичный канал, если бот туда не добавлен;
- нельзя получить старые посты до добавления бота;
- updates хранятся ограниченное время;
- удаление постов через Bot API отслеживается ограниченно;
- для групп privacy mode может скрывать сообщения.

Вывод: Bot API использовать для UX и realtime-потока новых постов из подключенных каналов.

### MTProto / userbot / TDLib

MTProto нужен, если требуется:

- импорт истории публичных каналов;
- импорт истории приватных каналов, куда есть доступ;
- reliable sync новых, отредактированных и удаленных сообщений;
- восстановление пропущенных updates;
- массовая первичная индексация.

Риски MTProto:

- нужен `api_id`, `api_hash`, номер телефона и защищенное хранение session-файлов;
- есть flood limits и риск блокировок;
- выше юридические и ToS-риски при несанкционированном scraping;
- нужно явно получать разрешение владельца/пользователя на индексацию каналов.

Вывод: для production лучше гибридная схема: Bot API для интерфейса, MTProto для разрешенного импорта истории и надежной синхронизации.

### Ссылки на источники

Для публичных каналов:

```text
https://t.me/<username>/<message_id>
```

Для приватных каналов и supergroups:

```text
https://t.me/c/<internal_channel_id>/<message_id>
```

Нужно хранить стабильные идентификаторы:

- `channel_id`;
- `channel_username`;
- `channel_title`;
- `message_id`;
- `date`;
- `edit_date`;
- `visibility`: `public`, `private`, `protected`, `unknown`;
- canonical source URL;
- raw Telegram payload.

Важно: username публичного канала может измениться, поэтому URL не должен быть единственным идентификатором.

## RAG-пайплайн

### 1. Ingestion

Задачи:

- получить список каналов;
- проверить доступ;
- загрузить историю, если разрешено;
- получать новые посты;
- сохранять raw-сообщения;
- обрабатывать edits и deletes;
- дедуплицировать по `channel_id + message_id` и `content_hash`.

### 2. Очистка текста

Правила:

- сохранять оригинальный raw text всегда;
- объединять `text` и `caption` в единое поле для индексации;
- нормализовать пробелы, переносы, Unicode;
- извлекать ссылки, хэштеги, упоминания;
- не удалять даты, числа, имена, тикеры, URL и хэштеги;
- удалять повторяющийся boilerplate только после накопления статистики;
- версионировать cleaning pipeline.

### 3. Чанкинг

Базовая стратегия:

- короткий Telegram-пост индексировать целиком;
- длинный пост делить по абзацам и предложениям;
- не смешивать разные посты в одном chunk;
- хранить связь chunk -> message -> channel;
- для генерации ответа передавать не только chunk, но и расширенный контекст поста.

### 4. Embeddings

Кандидаты:

- OpenAI `text-embedding-3-small` / `text-embedding-3-large`;
- BGE-M3;
- multilingual-e5;
- self-hosted sentence-transformers;
- Voyage multilingual embeddings.

Критерии выбора:

- качество русского языка;
- качество на коротких noisy Telegram-постах;
- стоимость batch indexing;
- latency;
- возможность self-hosting;
- размерность и стоимость хранения.

### 5. Хранилище и индексы

MVP-варианты:

- PostgreSQL + pgvector: проще инфраструктура;
- Qdrant + PostgreSQL: лучше специализированный vector search;
- OpenSearch/Elasticsearch: удобно для BM25 и больших текстовых индексов.

Практичный MVP: PostgreSQL для данных и pgvector или Qdrant для векторов.

Production-вариант: PostgreSQL + Qdrant/OpenSearch, если понадобится масштабирование и гибридный поиск.

### 6. Hybrid retrieval

Pipeline:

1. Принять запрос пользователя и выбранную область поиска: канал или пачка.
2. Выполнить full-text/BM25 search top 50.
3. Выполнить vector search top 50.
4. Объединить результаты через RRF.
5. Удалить дубликаты по `message_id` и `chunk_id`.
6. Применить фильтры по каналам, датам, языку и правам доступа.
7. Отправить top 50-80 кандидатов в reranker.
8. Передать top 5-10 источников в LLM.

### 7. Reranking

Задачи reranker:

- повысить precision;
- убрать похожие, но не отвечающие на вопрос посты;
- выбрать лучшие chunks для генерации;
- уменьшить вероятность галлюцинаций.

Кандидаты:

- bge-reranker-v2-m3;
- Cohere Rerank multilingual;
- Jina reranker;
- cross-encoder для русского/multilingual текста.

### 8. Генерация ответа

Контракт LLM:

- отвечать только по переданным источникам;
- не добавлять внешние знания, если они не подтверждены источниками;
- если ответа нет, честно сказать об этом;
- указывать источники с датами и ссылками;
- при противоречиях явно указать, что источники расходятся;
- сохранять краткость и практическую полезность ответа.

Пример формата:

```text
Краткий ответ:
...

Подробности:
- ...
- ...

Источники:
1. Канал, дата: ссылка
   Цитата: "..."
2. Канал, дата: ссылка
   Цитата: "..."
```

### 9. No-answer режим

Бот не должен отвечать, если релевантных источников нет.

Критерии отказа:

- reranker score ниже порога;
- найденные chunks не содержат ключевых сущностей запроса;
- источники похожи тематически, но не отвечают на вопрос;
- LLM не может привязать утверждения к источникам;
- найден только один слабый источник для вопроса, требующего подтверждения.

Пример ответа:

```text
В подключенных каналах я не нашел подтвержденной информации по этому вопросу.

Ближайшие найденные материалы не дают прямого ответа. Можно уточнить канал, период или ключевые слова.
```

- есть стратегия борьбы с boilerplate;
- есть `cleaning_version`.

### Субагент 6. Chunking strategy

Цель: выбрать стратегию разбиения постов для качественного поиска.

Задачи:

- сравнить post-level, paragraph-level, semantic chunking, sliding window и parent-child retrieval;
- определить размеры chunk и overlap;
- описать правила для коротких и длинных постов;
- описать связь chunk -> message -> source URL;
- продумать context expansion: полный пост, replies, media group, соседние посты;
- подготовить план A/B-теста чанкинга.

Критерии приемки:

- выбран baseline chunking strategy;
- chunks не смешивают разные посты;
- есть parent-child retrieval;
- есть metadata для цитирования;
- есть план сравнения стратегий.

### Субагент 7. Embeddings и vector DB

Цель: выбрать модель embeddings и хранилище векторов.

Задачи:

- сравнить OpenAI embeddings, BGE-M3, multilingual-e5 и self-hosted модели;

- оценить качество русского языка;
- оценить latency и стоимость индексации;
- описать batch indexing;
- описать reindex при смене модели;
- выбрать MVP и production варианты.

Критерии приемки:

- есть сравнительная таблица моделей;
- есть сравнительная таблица vector DB;
- выбран MVP baseline;
- описаны filtering requirements;
- есть стратегия версионирования embeddings.

### Субагент 8. Hybrid retrieval и reranking

Цель: спроектировать поиск, который работает и по смыслу, и по точным совпадениям.

Задачи:

- сравнить BM25-only, vector-only и hybrid search;
- выбрать алгоритм объединения результатов, например RRF;
- определить top-K для BM25, vector и reranker;
- описать boosts для точных совпадений: даты, имена, тикеры, hashtags, quoted phrases;
- выбрать reranker;
- описать diversity filtering и дедупликацию;
- описать fallback, если один из индексов недоступен.

Критерии приемки:

- выбран baseline hybrid algorithm;
- есть параметры top-K;
- есть правила score thresholds;
- есть дедупликация по message/chunk;
- есть latency budget;
- есть список retrieval-метрик.

### Субагент 9. Answer generation, citations и anti-hallucination

Цель: сделать ответы полезными, проверяемыми и безопасными от галлюцинаций.

Задачи:

- описать обработку противоречивых источников;

Критерии приемки:

## Предлагаемый roadmap

### Этап 0. Research и технические решения

Результаты:

- выбран стек MVP;
- описаны ограничения Telegram API;
- выбрана стратегия ingestion;
- выбрана стратегия RAG;
- сформирован evaluation plan.

### Этап 1. MVP без сложного автообновления

Состав:

- Telegram bot UI;
- ручное или полуавтоматическое подключение каналов;
- импорт ограниченной истории через MTProto или тестовый датасет;
- PostgreSQL для raw posts;
- базовый cleaning;
- post-level chunking;
- embeddings;
- vector search;
- ответ LLM с источниками;
- no-answer режим по простому threshold.

Definition of Done:

- бот принимает вопрос;
- ищет по выбранному каналу или пачке;
- возвращает краткий ответ;
- прикладывает ссылки на источники;
- не отвечает без найденного контекста.

### Этап 2. Пачки каналов и ACL

Состав:

- CRUD пачек каналов;
- добавление и удаление каналов из пачки;
- выбор пачки при поиске;
- права доступа к пачкам;
- приватные и публичные источники;
- логирование запросов.

Definition of Done:

- пользователь может создать пачку;
- поиск ограничивается выбранной пачкой;
- пользователь не получает ответы из недоступных источников;
- источники корректно маркируются как public/private/protected.

### Этап 3. Гибридный поиск

Состав:

- BM25 или PostgreSQL full-text search;
- vector search;
- RRF merge;
- reranker;
- score thresholds;
- boosts для дат, имен, hashtags и точных фраз.

Definition of Done:

- точные запросы работают лучше, чем в vector-only MVP;
- смысловые запросы сохраняют качество;
- false positives снижаются;
- no-answer становится надежнее.

### Этап 4. Автообновление индекса

Состав:

- listener новых постов;
- очередь задач;
- indexing workers;
- обработка edits;
- обработка deletes, если доступно через MTProto;
- periodic reconciliation;
- reindex pipeline.

Definition of Done:

- новый пост автоматически появляется в поиске;
- редактирование поста обновляет индекс;
- ошибки индексации ретраятся;
- можно переиндексировать корпус при смене модели embeddings.

### Этап 5. Качество, evaluation и feedback

Состав:

- eval dataset;
- benchmark retrieval;
- benchmark generation;
- пользовательские оценки ответа;
- dashboard качества;

Definition of Done:

- качество можно измерять до и после изменений;
- есть no-answer тесты;
- есть регулярный отчет по hallucination/citation accuracy;
- можно принимать решения на основе метрик.

### Этап 6. Advanced features

Состав:

- agentic retrieval;
- query rewriting;
- multi-query search;
- сравнение каналов;
- Knowledge Graph;
- fine-tuned classifiers/rerankers при наличии данных.

Definition of Done:

- сложные аналитические вопросы дают более полный ответ;

- агент ограничен по числу шагов и стоимости;
- все утверждения остаются привязанными к источникам.

## Главные риски

### Telegram API limitations

Bot API не умеет читать историю произвольных каналов. Для backfill нужен MTProto или другой разрешенный импорт.

Митигация:

- явно разделить режимы `new posts only` и `history import`;
- не обещать поиск по неподключенным каналам;
- строить собственный индекс.

### Галлюцинации LLM

Модель может додумывать факты, которых нет в источниках.

Митигация:

- строгий prompt contract;
- no-answer thresholds;
- обязательные источники;
- post-generation claim verification;
- evaluation на hallucination rate.

### Низкое качество retrieval

Vector search может пропускать точные совпадения, а BM25 может пропускать смысловые совпадения.

Митигация:

- hybrid retrieval;
- reranking;
- eval dataset;
- A/B-тест chunking и embeddings.

### Приватные каналы и права доступа

Ответ может содержать информацию из источника, недоступного пользователю.

Митигация:

- ACL с первого дня;
- tenant isolation;
- visibility для источников;
- consent flow;
- revoke access и удаление из индекса.

### Устаревание индекса

Посты редактируются и удаляются, новые публикации могут не попасть в базу.

Митигация:

- event-driven ingestion;
- periodic reconciliation;
- статусы обработки;
- reindex jobs;
- monitoring freshness lag.

### Стоимость и latency

Embeddings, reranker и LLM могут быть дорогими и медленными.

Митигация:

- кэш популярных запросов;
- лимиты top-K;
- дешевые модели для простых запросов;
- async processing;
- latency budget и cost monitoring.

## Открытые решения

1. Нужен ли импорт истории каналов в MVP или достаточно новых постов после подключения бота.
2. Какие источники разрешены: только owned channels или любые публичные каналы с consent flow.
3. Выбрать vector DB: pgvector для простоты или Qdrant для специализированного поиска.
4. Выбрать embedding-модель с хорошим качеством на русском языке.
5. Нужен ли OpenSearch на раннем этапе или достаточно PostgreSQL full-text.
6. Какой LLM-провайдер использовать для генерации.
7. Какие правила хранения логов пользовательских запросов допустимы.
8. Как обрабатывать protected content и приватные ссылки.

## Итоговая рекомендация

Начать с практичного MVP: Telegram bot + импорт разрешенных каналов + PostgreSQL + embeddings + vector search + LLM-ответ со ссылками. Сразу заложить модель пачек каналов, source metadata, ACL и no-answer режим.

После проверки MVP перейти к гибридному RAG: BM25 + vector search + reranker. Затем добавить event-driven автообновление индекса, evaluation benchmark и более строгую проверку groundedness.

Agentic retrieval, Knowledge Graph и fine-tuning не нужны на старте. Их стоит рассматривать только после появления стабильного корпуса, реальных пользовательских запросов и метрик качества.
